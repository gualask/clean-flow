# cf-cognitive

Runtime: [SKILL.md](../../skills/cf-cognitive/SKILL.md), shared [navigation-cost.md](../../skills/_shared/references/navigation-cost.md).

## Basis

- **Nesting ranks first; `else if` adds no level; a flat `switch` and a linear sequence are exempt.** Campbell, [Cognitive Complexity](https://www.sonarsource.com/docs/CognitiveComplexity.pdf) (SonarSource): nesting "increases the mental demands to understand the code"; for `else if` "the mental cost has already been paid when reading the if"; "A switch and all its cases combined incurs a single structural increment."
- **`try` counts as a block.** ESLint, [`max-depth` source](https://github.com/eslint/eslint/blob/main/lib/rules/max-depth.js): "TryStatement: pushBlock," while an else-if is not pushed.
- **A third nested block fires; a long simple case-statement is allowed.** Linux kernel, [Coding style](https://www.kernel.org/doc/html/latest/process/coding-style.html): "if you need more than 3 levels of indentation, you’re screwed anyway"; for "one long (but simple) case-statement … it’s OK to have a longer function."
- **Flatten the main path first.** Go, [Code Review Comments](https://go.dev/wiki/CodeReviewComments#indent-error-flow): "keep the normal code path at a minimal indentation".
- **level.** Beck, Composed Method ([c2 wiki](https://wiki.c2.com/?ComposedMethod)): "Keep all of the operations in a method at the same level of abstraction." Fowler, [FunctionLength](https://martinfowler.com/bliki/FunctionLength.html): code that takes effort to read is extracted and named "after that “what”".
- **level's bound and call order.** Ousterhout and Martin, [A Philosophy of Software Design vs Clean Code](https://github.com/johnousterhout/aposd-vs-clean-code): "if you trust the names of the methods being called then understanding the caller does not require understanding the callee" (Martin); two methods are "conjoined" when one cannot be understood without reading the other (Ousterhout). The skill takes Martin's ordering and Ousterhout's bound.
- **owner.** Parnas, [On the Criteria…](https://www.win.tue.nl/~wstomv/edu/2ip30/references/criteria_for_modularization.pdf) (1972): a module is characterized "by its knowledge of a design decision which it hides from all others." Release next to acquisition, reached on every exit: Effective Go, [Defer](https://go.dev/doc/effective_go#defer) ("the close sits near the open"); Rust, [OBRM](https://doc.rust-lang.org/nomicon/obrm.html); [PEP 343](https://peps.python.org/pep-0343/); Java [try-with-resources](https://docs.oracle.com/javase/tutorial/essential/exceptions/tryResourceClose.html). Stop from a lifecycle callback: React, [Lifecycle of Reactive Effects](https://react.dev/learn/lifecycle-of-reactive-effects) ("your cleanup function specifies how to stop synchronizing").
- **pure core.** Bernhardt, [Functional Core, Imperative Shell](https://www.destroyallsoftware.com/screencasts/catalog/functional-core-imperative-shell): the shell does I/O "based on values produced by the functional core."
- **consistency.** [PEP 8](https://peps.python.org/pep-0008/#a-foolish-consistency-is-the-hobgoblin-of-little-minds): "Consistency within a project is more important. Consistency within one module or function is the most important."
- **Length is a soft signal near 20 lines.** Fowler, [FunctionLength](https://martinfowler.com/bliki/FunctionLength.html): length "is a proxy for the more important question - when should we enclose code in its own function?" Martin, quoted in the [debate](https://github.com/johnousterhout/aposd-vs-clean-code): "Functions should hardly ever be 20 lines long".
- **Preservation claimed only after the tests pass.** Fowler, [SelfTestingCode](https://martinfowler.com/bliki/SelfTestingCode.html): confidence comes "should the tests pass". Liu et al., [LLMs in Automated Software Refactoring](https://arxiv.org/abs/2411.04444) (2025): some LLM refactorings "changed the functionality of the source code".
- **Navigation cost is finding and reading.** Ko et al., [How Developers Seek, Relate, and Collect Relevant Information](https://faculty.washington.edu/ajko/papers/Ko2006SeekRelateCollect.pdf) (TSE 2006): developers spend "35 percent of their time performing the mechanics of navigation".
- **Naming test.** Martin in the [debate](https://github.com/johnousterhout/aposd-vs-clean-code): extracted code "can be given a descriptive name; and that it does less than the original method." React, [Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks): "If you struggle to pick a clear name, it might mean … is not yet ready to be extracted."
- **Group what is read together.** Letovsky and Soloway, [Delocalized Plans](https://www.cs.kent.edu/~jmaletic/cs69995-PC/papers/letovsky-1986-software.pdf) (1986): "delocalized plans are more liable to misinterpretation than plans whose code is closely grouped."
- **File and directory triggers.** ESLint, [`max-lines`](https://eslint.org/docs/latest/rules/max-lines): "default 300". Angular, [Style 04-04 Flat](https://github.com/angular/angular/blob/17.3.x/aio/content/guide/styleguide.md): "when a folder has ten or more files, it may be time to create subfolders."
- **No splitting an indivisible owner.** Ousterhout in the [debate](https://github.com/johnousterhout/aposd-vs-clean-code): "As methods get smaller and smaller there is less and less benefit to further subdivision."
