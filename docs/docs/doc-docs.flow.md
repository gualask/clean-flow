# cf-docs Flow

## Purpose

Document the runtime flow for `cf-docs`, the public entrypoint for writing documentation — authoring, updating, trimming, or restructuring it — and for auditing existing docs against the code, so they stay accurate, lean, and free of duplicated concepts.

The routing boundary is one rule: use the skill when the request writes a Markdown file outside `.cflow/`, or asks to audit existing docs against the code; do not use it otherwise. The description names the files people ask for (README, CHANGELOG, AGENTS.md or CLAUDE.md) as trigger words and states only when to use the skill: the earlier opening sentence ("Write accurate, lean, nonduplicative documentation") told how to write, which the description must not do. Not used to read a doc to answer a question, for a todo file (`cf-todo`), or for files under `.cflow/`.

## Runtime Inputs

- Public skill: `skills/cf-docs/SKILL.md`
- Runtime references: `skills/cf-docs/references/review.md`, `generate.md`, `reorganize.md`; read when the target is that file: `changelog.md`, `agents-md.md`
- Target artifacts: none

## High-Level Flow

1. Start from the docs the request targets, or the thing to be documented.
2. Choose the review, generate, or reorganize flow from the current request. There is no ambiguity question (removed 2026-10-27, as in cf-cognitive and cf-placement, where removing it did no harm); "Do not infer authoring from words like review" stays, because it is the line that prevents the edit.
3. When the target is a CHANGELOG, or an AGENTS.md or CLAUDE.md, also read that file's reference. The project README has none: with and without a README reference the 2.0 README of a release came out the same (154 and 153 lines, user-facing, build in a `<details>`, a version-named section), so the reference was cut.
4. Apply the core rules in every flow: accuracy, duplication (search the docs before writing a fact; a fact another doc owns gets a link; when the new doc becomes the owner, the old copy becomes a link), leanness, implementation detail, structure, language (the repository's docs language; AGENTS.md and CLAUDE.md in English), scope.
5. In review, run the accuracy, duplication, leanness, and structure passes; report findings and edit only when fixes or trimming are requested. Trimming removes restated content, history that gives no reason for the current design, and decoration, never a fact no other doc or source comment carries.
6. Leave implementation detail in the doc and report it as a candidate move to a source comment unless the request authorizes source edits.
7. In generate, ground content in the code, choose one doc purpose, place each concept once, and say where the new doc should be linked from.
8. In reorganize, group docs by an aspect they share, with at least two docs per group and at most one level under `docs/`; move whole files and keep their names unless one no longer fits; present the target tree and end the turn; apply it after the user confirms; write no new docs or sections, and put what looks missing or duplicated in **Result**; keep one index.
9. Verify concrete claims against the code and validate links and anchors before finishing.
10. Report scope and flow, findings (including duplication across and within docs), changes with the owner doc for each duplicated concept and where the facts of each removed passage now live, checks, and next action.

## Design Basis (2026-10-27)

Goal: do for Markdown what the rest of the pack does for source. Keep `docs/` in a shallow tree grouped by aspect, keep docs lean for a model reader, place each concept once, and give files with their own rules (CHANGELOG, AGENTS.md) a reference each, read only when that file is the target. A line enters the skill only where the model without the skill misses it.

Sources, each read on the page on 2026-10-27:

- **Tree.** Diátaxis, [How to use Diátaxis](https://diataxis.fr/how-to-use-diataxis/): it "does not mean that you should create empty structures for tutorials/howto guides/reference/explanation … with nothing in them", and it "discourages planning and top-down workflows", preferring "small, responsive iterations from which overall patterns emerge". The four kinds rule what a page holds, not which folders exist. Rule: a group is born when its documents exist, never ahead of them.
- **One owner per fact.** Write the Docs, [Documentation Principles](https://www.writethedocs.org/guide/writing/docs-principles/): "Eliminate content overlap between separate sources", with "the scope of each source … clearly defined and disjoint". The same page accepts "(some) Repetition In Documentation": strict DRY "won't get far". Rule: repetition is allowed only as the minimum context a reader needs.
- **Lean for a model reader.** Gloaguen et al., [Evaluating AGENTS.md](https://arxiv.org/html/2602.11988): "context files are not effective at providing a repository overview"; with all other documentation removed, LLM-generated context files "improve performance by 2.7% on average", that is, they repeat the existing docs; they "should only contain specific additional instructions beyond what is already available in the codebase". Counterweight: ACE, [arXiv:2510.04618](https://arxiv.org/abs/2510.04618), names "brevity bias, which drops domain insights for concise summaries". Rule: leanness removes what the code or another doc already carries, never a fact found nowhere else.
- **README.** Google, [READMEs](https://google.github.io/styleguide/docguide/READMEs.html): "A README is a short summary of the contents of a directory"; "At a minimum … a link to your user- and/or team-facing documentation". GitHub, [About READMEs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes): "only … information necessary for developers to get started using and contributing"; "Longer documentation is best suited for wikis." Rule: the project README faces users, with what the project is, how to start, and an index into `docs/`. The model without the skill already writes it that way (see Measured), so no reference carries it.
- **CHANGELOG.** [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/): "Changelogs are for humans, not machines"; latest first, dated, linkable; `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`; an `Unreleased` section at the top; "Using commit log diffs as changelogs is a bad idea: they're full of noise." [Common Changelog](https://common-changelog.org/), "a stricter subset": `Changed`, `Added`, `Removed`, `Fixed` in that order; no `Unreleased`; "no more than one line long"; never excludes refactorings. The two conflict on `Unreleased`, on `Deprecated` and `Security`, on category order, and on commit references.
- **AGENTS.md.** Claude Code, [Best practices](https://code.claude.com/docs/en/best-practices): "every line in it takes a little of Claude's attention on every task"; it lists "Describe your architecture and file layout" as outdated advice, because "Claude reads the repo itself"; keep what the model cannot see, including "Anything you've had to correct twice already"; "piling on emphasis mostly makes Claude over-apply the rule". Claude Code, [Memory](https://code.claude.com/docs/en/memory): its checkup "cuts content Claude can derive from the codebase, such as directory layouts, dependency lists, and architecture overviews, and keeps pitfalls, rationale, and conventions that differ from tool defaults"; "if two instructions contradict each other, Claude may pick one arbitrarily".

Decisions of the user:

- CHANGELOG: keep the standard the repository already follows; a new changelog follows Keep a Changelog 1.1.0 with SemVer.
- AGENTS.md: no repository layout. A directory appears only with a rule the model cannot infer, such as generated migrations that are never edited by hand. Keep verification commands, conventions that differ from tool defaults, places where the code misleads, and decisions that live outside the repository, each with its reason. Always in English: the model reads it, as it reads the skills (no measurement found that English performs better).
- Reorganization: moving and renaming are invasive, so the target tree is confirmed before any file moves.

- **Reorganize**: no skill kept links and source-comment paths right (0 broken in every run) but wrote new docs: ~68 and ~330 lines, a one-file folder, renames beyond the move; on an already organized repository it touched 37 files (+512/−392) and split a doc into small guides. The previous skill had no reorganize flow, took generate, and rewrote more (+920/−769 on one repository). Current: the first turn presents the tree and touches nothing (3 of 3); after "proceed", moves only (16 and 12 renames, +40/−29 and +49/−42, 0 broken links, source comments updated); on the organized repository it proposed two moves.

- **Description** (only when to use, with the files people ask for as trigger words): README, CONTRIBUTING, CHANGELOG, and CLAUDE.md requests opened the skill (4 of 4, CLAUDE.md read `agents-md.md`); a todo.md request opened `cf-todo`; a question about what the README says opened no skill and touched no file.
- **Ablation** of two core sentences, one run per cell: without "when the doc being written becomes the owner, replace the old copy with a link", the new batch-compression doc took over the section of `pdf-export.md` but `performance.md` kept its copy of two facts; with it both old copies became links. Without "do not copy what the code holds", no value was copied in either run (`generate.md` already links the owning constant), so that sentence was cut.

- **Output slots** (gpt-6-luna max, same cells, current skill against one without **Scope** and with **Changes** as one removed passage per line with its new path): without Scope no answer kept the bold slot form (0 of 7, headings instead, one with the slot names translated), with it 5 of 7; the per-line Changes still came out as a summary. Scope stays, Changes unchanged.

A README reference sending developer content to `CONTRIBUTING.md` moved it out on one repository of two; four wordings of "keep an existing fact unless the code or a source contradicts it" (core Accuracy rule, `generate.md`, long and short) still dropped the section, judged stale. No line added; declared cost.

- **Review flow** (gpt-6-luna max, one run per arm): asked whether the docs still match the code after the TanStack change, no skill and the current skill both found the two stale cache sections and edited nothing (4 and 6 more drifts found). Trimming a 326-line `pdf-export.md` that repeats itself: both arms ~90 lines, only that file, repetitions to one; with the skill "meaningfully smaller" became the 5% in the code, `Light` 220 DPI was added, facts the README carries became links, and **Changes** named the test files holding the removed checklist, but the reason for the classic writer (object streams did not open in PDFKit) was cut as a historical note, while no skill kept it. With Leanness allowing only history "that gives no reason for the current design", it stayed and **Result** flagged it as unverifiable in the repository.

Noise kept: the first reorganize turn closes with a sentence quoting the skill's rule to justify the question (3 of 3), and it also reads the README and AGENTS.md references.
