## Basis

- **Groups are born from existing docs.** Diátaxis, [How to use Diátaxis](https://diataxis.fr/how-to-use-diataxis/): it "does not mean that you should create empty structures for tutorials/howto guides/reference/explanation … with nothing in them", and it "discourages planning and top-down workflows", preferring "small, responsive iterations from which overall patterns emerge". Hence a group needs two existing docs, and reorganizing writes no new doc.
- **One purpose per section.** Diátaxis separates tutorials, how-to guides, reference and explanation by the reader's need; the Structure rule keeps how-to, reference and explanation out of one section.
- **One owner per fact.** Write the Docs, [Documentation Principles](https://www.writethedocs.org/guide/writing/docs-principles/): "Eliminate content overlap between separate sources", with "the scope of each source … clearly defined and disjoint"; the same page accepts "(some) Repetition In Documentation", since strict DRY "won't get far". Hence a link instead of a second explanation, and the old copy becomes a link when the new doc takes ownership.
- **Lean, never at the cost of a unique fact.** Gloaguen et al., [Evaluating AGENTS.md](https://arxiv.org/html/2602.11988): "context files are not effective at providing a repository overview"; they "should only contain specific additional instructions beyond what is already available in the codebase". Counterweight, ACE, [arXiv:2510.04618](https://arxiv.org/abs/2510.04618): "brevity bias, which drops domain insights for concise summaries". Hence trimming removes what another doc or the code carries, and keeps a fact found nowhere else.
- **CHANGELOG.** [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/): "Changelogs are for humans, not machines"; an `Unreleased` section at the top; "Using commit log diffs as changelogs is a bad idea: they're full of noise." [Common Changelog](https://common-changelog.org/), "a stricter subset", conflicts with it on `Unreleased`, categories and their order, so the reference keeps the format the repository already follows and defaults to Keep a Changelog.
- **AGENTS.md and CLAUDE.md.** Claude Code, [Best practices](https://code.claude.com/docs/en/best-practices): "every line in it takes a little of Claude's attention on every task"; it lists "Describe your architecture and file layout" as outdated advice because "Claude reads the repo itself", and keeps "Anything you've had to correct twice already". Claude Code, [Memory](https://code.claude.com/docs/en/memory): its checkup "cuts content Claude can derive from the codebase, such as directory layouts, dependency lists, and architecture overviews, and keeps pitfalls, rationale, and conventions that differ from tool defaults".

- **Todo: every task has a done criterion; ask when it is missing.** Wake, [INVEST in Good Stories, and SMART Tasks](https://xp123.com/invest-in-good-stories-and-smart-tasks/) (2003): "The key measure is, “can we mark it as done?”"
- **Todo: durable rationale goes to an owning doc, not the todo file.** Nygard, [Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions): "We will keep a collection of records for "architecturally significant" decisions".

## No external source

- Confirming the target tree before any file moves: the user's decision, since moving and renaming are invasive.
- AGENTS.md and CLAUDE.md always in English: the user's decision; no measurement found that English performs better.
- Keeping historical notes that give the reason for the current design: the pack's own runs.
- Todo file: one ordered file; GFM checkboxes; the default path and extending an existing file; the two sections; checking tasks in place and the rollover rule; routing an open question to `cf-mr-wolf`; only Language and Scope of the Core Rules; recording the session's decisions as given, not checked against the code; a review or test finding recorded as an open question with its evidence and route until the user decides it: the pack's own runs.
