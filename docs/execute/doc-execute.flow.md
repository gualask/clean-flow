# cf-execute Flow

## Purpose

Maintainer summary for `cf-execute`, which plans and implements an approved spec: a structural spec from `cf-architecture` or a feature spec from `cf-brainstorm`. Runtime behavior belongs to `skills/cf-execute/SKILL.md` and its linked references; keep this file descriptive, not authoritative.

## Runtime Inputs

- Public skill: `skills/cf-execute/SKILL.md`
- Phase references: `skills/cf-execute/references/*.md`
- Shared sources vendored into runtime paths: configured `skills/_shared/references/*.md`; `skills/_shared/scripts/dir-population.mjs` for the split placement count
- Artifact template: `skills/cf-execute/assets/execution-plan.template.md`
- Input artifact: the approved spec under `.cflow/specs/`, owned by the skill that wrote it
- Target artifact: `.cflow/execution-plan.md`

## Maintainer Notes

- Controller runtime stays in `skills/cf-execute/SKILL.md`; phase rules stay in `skills/cf-execute/references/*.md`.
- Three cross-phase rules are stated once in `SKILL.md`: spec authority (read, never edit or redesign; a conflict is named and asked), execution authorization (one explicitly requested accepted unit), and scope (spec or unit, repository over artifacts). Phases are reference lists; references say only where to record a deviation.
- The Spec Gate replaces cf-start's Frame Gate, assessment, and target shape. It looks for the spec and plan with `ls` (`.cflow` is git-ignored, so `rg` skips it). Without an approved spec or accepted plan it does not plan: it hands the request to `cf-architecture`, `cf-mr-wolf`, or a local skill and follows that skill in the same turn (measured: the no-spec refactor request ran architecture's first turn, no files; a bounded edit ran `cf-cognitive`, no plan). An undesigned feature goes to `cf-mr-wolf`, not `cf-brainstorm`: brainstorm accepts only an explicit user request and handed it back to mr-wolf (1 run); pointed at mr-wolf directly, the same request got mr-wolf's question with no plan and no files (1 run, 2026-09-30).
- A `draft.md` is never an approved spec: the Spec Gate hands it back to its `owner`, which promotes it. Measured: "Va bene, procedi." after architecture asked to approve the spec sent the model into execute planning from the draft, skipping promotion.
- `.cflow/execution-plan.md` names the spec path and records units, state, and drift. It does not copy the spec's design; the former `Assessment summary` and `Target direction` fields are gone. The template keeps only fields a reference reads, plus the two pressure sections: without them every structural unit was planned `feature` (1 run); with them and the mode definition, two structural plans gave the same five `split` units at 96–98 lines against 122–141 with the full template, and WU-01 ran the split path to `done` with the suite green (2026-10-01).
- Planning: a structural spec with target and `Moves` goes through `migration-unit-planning.md`, any other spec through `work-unit-planning.md`. A small spec can be one unit. Units are `split`, `consolidate`, or `feature`, defined once in `SKILL.md` Planning by what the unit does to existing code: the structural chain reads only `migration-unit-planning.md`, which never named the modes, and the pack labeled the same contract move `split` in one run and `consolidate` in another.
- Keep planning and execution as separate gates; execute one accepted unit per invocation unless asked otherwise. On resume, the recommended next unit is named and confirmed before execution; a continue request runs only the active unit (measured: "Riprendiamo il lavoro" otherwise executed the recommended unit).
- One name per concept across the references: the plan is `accepted`, `live` is its read state, `approved` is only the spec; the unit's scope is `touched scope`; planning, review and verify close with `Recommended next action`, unit execution with the standard `Output Format` (Changes, Checks, Result). The unit's move is the spec's decision: when the code contradicts the plan or the spec, execution records it in `Decision notes` and asks; one ad hoc bed with an unjustified split executed the move without asking under two wordings, 1 of 1 each, so the line is text coherence, not measured behavior. Names pass measured on five cells (unit, review, verify, cleanup, resume), no regression (2026-10-21). `review.md` defines a closure challenge at first use as the user challenging a unit marked done; measured once (2026-10-21): the challenge re-reviewed the done unit against the worktree and its untracked files, kept the verdict, touched no source and left the pending units alone.
- Cleanup after a unit, only on an explicit request, follows `cf-cognitive` on the unit's touched scope: the remedy for function-level pressure lives in that skill. `local-simplify.md` and the shared `local-refactor-rules.md` are gone; the latter made no difference to the refactor in cf-cognitive (same refactor with and without, 2026-10-22 and 2026-10-24). Measured 2026-10-25 on a done move unit whose touched scope holds a 25-logical-line function: the cleanup request read `cf-cognitive`, measured, kept the functions whole by its four tests and edited nothing, full check and behavior oracle green (1 run); the old reference renamed one local in scope and updated the plan (1 run).
- Review reports each function in the touched scope past 20 logical lines as a cleanup candidate routed to `cf-cognitive`, without blocking closure, as cf-review's lens 8 does; the shared `local-readability-review.md` is gone. Same bed, 2026-10-25: the route named the function with its file and line as optional `cf-cognitive` cleanup and recommended `stop` (1 run); the old reference and the bare model did not name it (1 run each). No source edits in any arm.
- Every unit runs one reference, `unit-execution.md` (309 tokens): lock the preserved behavior before editing (the tests over the touched scope, characterization where none covers what moves), only this unit, regression handling when a check breaks, reference audit when names or files move, the full check before `done`, the plan updated. It replaced the split and consolidation chains (concentration and fragmentation maps, safety net, split and consolidation execution, structural closure: about 1,800 tokens, plus the 2,276 of `file-split-rules.md` and `navigation-cost.md` the split path read). Measured 2026-10-26 on a VS Code extension with sandbox network, gpt-6.1-sol high, one run per arm: on an accepted plan's `split` unit (LOC run invocation and cancellation moved into a core session) the bare model, the full pack and the cut version all kept a behavior oracle 5 of 5 (replacement, cancellation, old cleanup leaving the new run cancellable), characterized before moving, stayed in the unit and fixed the doc reference to the removed file (bare 1 of 2); only the bare model skipped the full check (0 of 2: no knip, no full suite), the pack and the cut version ran it (pack 4.3 min, 709k input; cut 4.2 min, 656k). On a whole-feature `feature` unit the cut version ran the suite before editing, added tests for all five behaviors the spec names, ran the full check before `done` and added nothing outside the spec (1 run). The maps' and execution references' lines produced nothing the bare model did not do given the plan; the plan itself still carries characterization and validation, so a plan written without the pack is untested. `consolidate` units keep no criteria of their own beyond the spec (no bed).
- No architecture criteria in execution: placement decisions belong to the spec. Measured: on a brainstorm-style feature spec that left placement open, execution put the shared state in the VS Code adapter with and without `architecture-principles.md` (1v1, 2026-09-29).
- Migration-unit planning surfaces the plan's most fragile assumption before approval, and keeps only that, the missing-inputs stop and one first unit. Measured 2026-10-26 on an approved structural spec with four migration steps, one run per arm: the bare model followed the order and the `Moves`, named the run-identity risk and stopped, but wrote no fragile assumption, no checkpoint question, no current or next unit, and added a README/CHANGELOG/docs step the spec did not ask for; the full pack and the cut version (without "no big-bang", "follow the `Moves` and migration order", "narrowest first unit", "behavior-preserving" and "temporary staging") both gave three units in the spec's order with modes, coherent state, the fragile assumption with its cheapest check and the checkpoint question (pack 3.5 min, 382k input; cut 3.0 min, 258k).
- Closure runs the repository's full check command (`test` script or CI command) before a unit is marked `done`; a failing full check keeps the unit `active`. Measured: a split unit that ran only the plan's narrower validation left lint failing and was marked `done`.
- When a safety lock or check breaks during execution, `regression-handling.md` (shared, vendored) gates further edits: root-cause sentence, three-hypothesis hard stop, scope blast after the fix.
