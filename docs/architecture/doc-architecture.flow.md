# cf-architecture Flow

## Purpose

Assess and propose repository or subsystem architecture, including exploration without a known problem. Worth-doing or impact judgments about a named change belong to `cf-scenario`.

## Runtime Contract

[SKILL.md](../../skills/cf-architecture/SKILL.md) (659 tokens, rewritten 2026-10-20 from a 1012-token body of per-row instructions) holds the whole first-turn procedure; no reference is read before the user replies.

Propose the target tree from repository evidence (code, tests, docs, dependencies, history), not directory styles. With no stated goal, assume behavior preservation, modifiability and testability of the present system; do not invent future needs. Attend to separation of responsibilities, ownership (one decision made in more than one place gets the place where it is made once), coupling and cohesion, abstractions missing or serving nothing, and smells. Two rules decide ownership: a state or policy belongs to the capability when any interface invoking the use case would need it (lifecycle, cancellation, result acceptance, cache, workflow rules, or an analogous one) and to an adapter only when one environment or presentation session causes it, judged on the decision and not on the framework mechanism or where it runs, with no tree while such a behavior sits in an adapter; and a new adapter or contract only separates variants the code already implements in separate modules. For each dimension the code varies along (platform or build target, provider, storage, configuration, or an analogous one) the skill names the variants, every place that chooses among them in code, build conditions and UI, and where the choice should be made once; where the variants have implementations of their own it runs the bundled `scripts/variant-history.mjs` (vendored from `_shared`, resolved from the active skill root) with those directories, and cites its per-commit list of files changed outside the variant as evidence, writing no count of its own.

Output: one target tree with, under each directory, what it owns and the `file:line` that proves it, then what stays with the same evidence; no plan, priorities or steps until the user replies to the tree; nothing implemented, no file created.

Measured (2026-10-20) on a VS Code extension and a Tauri app with their real history, gpt-6.1-sol at effort high, two runs per repository: the script ran from the skill path in 4 of 4 runs, two or three times per run with the model's own `--rev` and `--max` choices, every quoted number and file list exact when recomputed on the bed, and each run noted that an initial or mixed commit does not measure a variant's cost by itself; the panel-owned scan lifecycle with its LOC cycle went to the capability in 2 of 2 while the root choice, timers and webview stayed in the host; the duplicated Win32/POSIX path rule got one place in 2 of 2 with no new port; the stop timeout, the microphone-mode rule and the run catalogue left the command handlers in 2 of 2; the transcription defaults left `shared` in 2 of 2; the UI's `isWindows` branches were replaced by modes the capability exposes in 2 of 2; the silence and punctuation rules left the ORT engine in 2 of 2; no invented adapter or contract in 4 of 4, with the single-storage repository refused explicitly each time; no harmful move; a tree with ownership per directory and no plan in 4 of 4; 77 of 110 `file:line` links sampled, all true; 3.1–4.3 minutes and 0.66–1.19M input tokens against 5.5 minutes and 1.7–2.6M for the previous body on the same model. The first answer is a recommendation in the conversation and creates no files; a recommendation to keep the structure ends there. When the user replies to a recommendation that changes the structure, the skill reads its private [spec reference](../../skills/cf-architecture/references/spec.md), which runs the shared draft → spec cycle ([design-spec-lifecycle.md](../../skills/_shared/references/design-spec-lifecycle.md)) with that reply as the first decision. The spec holds the target tree with its ownership and evidence, a `Moves` table (what moves, from → to, the decision it carries with file:line, the evidence its current owner is wrong; no evidence, no move; only moves from the approved recommendation, while a change found while writing becomes an open question) and the migration order. An approved spec ends the skill: promotion ends the turn with the spec path and `cf-execute` named for the user to invoke, without opening it or starting to plan. The skill does not implement changes.

Feature handoff: when `cf-brainstorm` hands over its draft, product decisions are settled. The skill decides ownership only for what the feature adds or changes, as the target tree of the touched modules; a problem outside them is one line outside the tree. The spec keeps brainstorm's sections and adds that tree and `Moves` only for existing code the feature must relocate. Measured: without the scope limit, one of two runs inventoried every `shared` module. Not re-measured after the 2026-10-20 rewrite.
