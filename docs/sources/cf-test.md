## Basis

- **No observable contract, no candidate.** Kuefler, [Unit Testing](https://abseil.io/resources/swe-book/html/ch12.html) (*Software Engineering at Google*): "make calls against its public API rather than its implementation details."
- **Invariants never read from the implementation; candidates stay candidates.** Konstantinou et al., [Can we find bugs using LLM-generated oracles?](https://arxiv.org/abs/2410.21136): generated oracles "mirror the program's actual behavior rather than the expected one". Barr et al., [The Oracle Problem](http://www0.cs.ucl.ac.uk/staff/M.Harman/tse-oracle.pdf) (TSE 2015): without an adequate source "the final source of test oracle information remains the human".
- **Lens 1, a missing invariant shown by a regression that still passes.** Google, [What to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html): "Will the tests actually fail when the code is broken?" Vera-Pérez et al., [Pseudo-tested Methods](https://arxiv.org/abs/1807.05030) (EMSE 2019): methods "covered by the test suite, yet no test case fails when the method body is removed".
- **`remove` first.** Khorikov, *Unit Testing Principles* ([chapter 1](https://enterprisecraftsmanship.com/files/Unit-Testing-Chapter-1-Excerpt.pdf)): "Keep only tests of positive net value in the suite".
- **Lens 2, a negative assertion on calls needs a contract.** Trenk & Bly, [Test Doubles](https://abseil.io/resources/swe-book/html/ch13.html): interaction testing is warranted when "Differences in the number or order of calls to a function would cause undesired behavior".
- **Lens 3, invalid states representable.** Minsky, [Effective ML Revisited](https://blog.janestreet.com/effective-ml-revisited/): "Make illegal states unrepresentable". King, [Parse, don't validate](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/).
- **Lens 4, redundant rows.** [Equivalence partitioning](https://en.wikipedia.org/wiki/Equivalence_partitioning): "test cases are designed to cover each partition at least once".
- **Lenses 5–7, brittleness.** Kuefler, [Unit Testing](https://abseil.io/resources/swe-book/html/ch12.html): "a brittle test is one that fails in the face of an unrelated change to production code that does not introduce any real bugs." Meszaros, [Fragile Test](http://xunitpatterns.com/Fragile%20Test.html): Overspecified Software, "the tests describe how the software should do something, not what it should achieve"; Sensitive Equality, objects "converted to strings and compared with an expected string". Fowler, [Mocks Aren't Stubs](https://martinfowler.com/articles/mocksArentStubs.html): "Mockist tests are thus more coupled to the implementation of a method."
- **Lens 8, setup copied across test files.** Meszaros, [Test Code Duplication](http://xunitpatterns.com/Test%20Code%20Duplication.html): duplicated test code "must be maintained every time the system under test (SUT) is modified in a way that affects the semantics (number of arguments, argument attributes, returned object attributes, calling sequences) of its methods"; remedies Test Utility Method and Creation Method; cause "Reinventing the Wheel", "a lack of awareness of what Test Utility Methods are available".
- **Lens 9, outcome that changes without a code change.** Luo et al., [An Empirical Analysis of Flaky Tests](https://huang.isis.vanderbilt.edu/cs8395/paper/flakytest.pdf) (FSE 2014): "The top three categories of flaky tests are Async Wait, Concurrency, and Test Order Dependency"; "About third of Async Wait flaky tests (34%) use a simple method call with time delays to enforce orderings"; "Most flaky tests (78%) are flaky the first time they are written."; Time: "Relying on the system time introduces non-deterministic failures"; Randomness: tests "use a random number generator without accounting for all the possible values that may be generated"; Unordered Collections: "the code should not assume that the elements are returned in a particular order"; Network: "the network is a resource that is hard to control"
- **Lens 10, a higher-layer case that repeats a test of the delegated unit.** Vocke, [The Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html), "Avoid Test Duplication": "If you have tested all conditions confidently on a lower-level test, there's no need to keep a higher-level test in your test suite"; "You don't test all the conditional logic and edge cases that your lower-level tests already cover in the higher-level test again"; "I delete high-level tests that are already covered on a lower level (given they don't provide extra value)". One case per higher-layer branch: [Equivalence partitioning](https://en.wikipedia.org/wiki/Equivalence_partitioning), "test cases are designed to cover each partition at least once".
- **Seams that are contracts.** Khorikov, [When to Mock](https://enterprisecraftsmanship.com/posts/when-to-mock/): "Intra-system communications are implementation details"; the way the system talks to the external world: "It's part of the contract".
- **No style candidates.** Panichella et al., [Test smells 20 years later](https://digitalcollection.zhaw.ch/handle/11475/25672) (EMSE 2022): multiple smells "virtually never correlated with semantic or maintainability flaws".
- **Context gate and recap file** (shared with cf-clean): see the [cf-clean mirror](./cf-clean.md).

## No external source

Kept on the pack's own runs or on the user's decision: a source's silence is not evidence; existing tests or documents count as authoritative only when designated or when they name the behavior; lens 2's `remove` side; lens 2 on negative assertions other than calls (empty stderr, no mutation in dry-run, cleanup); one candidate per test case or table; scope selection; lens 3 prescribing no type shape; the `low` tier and the action order; the policy band from the script; working through a recap.
