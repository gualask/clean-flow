## Basis

- **Decompose from the drivers, as far as the risks ask.** Bass, Clements and Kazman, [Attribute-Driven Design](https://people.ece.ubc.ca/matei/EECE417/BASS/ch07lev1sec2.html) (*Software Architecture in Practice*): "The module to start with is usually the whole system."; "We will base our decomposition of a module on the architectural drivers." Fairbanks, [Just Enough Software Architecture](https://www.georgefairbanks.com/book/): "There is no need for meticulous designs when risks are small". Hence `Drivers`, then `Form`, then each split only where its condition holds.
- **Forms compared on the drivers, each with a drawback.** Borowa, Rebouças de Almeida and Wiese, [Debiasing Architectural Decision-Making](https://arxiv.org/abs/2502.04011) (ICSA 2025): "anchoring can cause architects to unconsciously prefer the first architectural solution that they came up with"; "Listing at least one drawback of the solution alternative: This technique is targeted towards countering the effects of anchoring, since anchoring often makes practitioners over-focused on one solution's advantages". [MADR](https://adr.github.io/madr/): "Decision Drivers", "Considered Options", each option with "Good, because" and "Bad, because", and a chosen option justified as the one "which resolves force {force}".
- **Entry points, business logic, persistence, then modules.** Fowler, [Presentation Domain Data Layering](https://martinfowler.com/bliki/PresentationDomainDataLayering.html): "One of the most common ways to modularize an information-rich program"; "that's OK for smaller systems, but once any of these layers gets too big you should split your top level into domain oriented modules which are internally layered". Evans's bounded context ([Fowler, BoundedContext](https://martinfowler.com/bliki/BoundedContext.html)): "you need a different model when the language changes."
- **When an application service pays.** Stafford, [Service Layer](https://www.informit.com/articles/article.aspx?p=1398617&seqNum=4) (*Patterns of Enterprise Application Architecture*): "You probably don't need a Service Layer if your application's business logic will only have one kind of client"; "as soon as you envision a second kind of client, or a second transactional resource in use case responses". A persistent store is his transactional resource, extended to stores with no shared transaction. Evans, in Fowler's [AnemicDomainModel](https://martinfowler.com/bliki/AnemicDomainModel.html): "This layer is kept thin."
- **Separate deployables last.** Fowler, [MonolithFirst](https://martinfowler.com/bliki/MonolithFirst.html): "even experienced architects working in familiar domains have great difficulty getting boundaries right at the beginning."
- **One owner per decision.** Parnas, [On the Criteria To Be Used in Decomposing Systems into Modules](https://www.cs.lafayette.edu/~gexia/cs301/resources/parnas.html) (CACM 1972): "one begins with a list of difficult design decisions or design decisions which are likely to change. Each module is then designed to hide such a decision from the others."
- **Business logic apart from its delivery.** Cockburn, [Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture/): "Allow an application to equally be driven by users, programs, automated test or batch scripts"; "code pertaining to the inside part should not leak into the outside part". This is the capability-or-adapter test: a policy every driver needs is inside. Martin, [The Clean Architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html): "source code dependencies can only point inwards"; "Your business rules are not bound to the database."
- **Stated structure against the code, and no cycles.** Murphy, Notkin and Sullivan, [Software Reflexion Models](https://www.cs.ubc.ca/~murphy/papers/rm/fse95.html) (FSE 1995): high-level models "are almost always inaccurate with respect to the system's source code"; a reflexion model "shows where the engineer's high-level model agrees with and where it differs from a model of the source." Li, Liang, Soliman and Avgeriou, [Understanding Architecture Erosion: The Practitioners' Perceptive](https://arxiv.org/abs/2103.11392) (ICPC 2021): "This divergence between the intended and the implemented architecture is often called architecture erosion"; among its symptoms, "the accumulation of cyclic dependencies and increased coupling, both resulting in binding elements together that were intentionally separated by architects." Martin's [Acyclic dependencies principle](https://en.wikipedia.org/wiki/Acyclic_dependencies_principle): "the dependency graph of packages or components should have no cycles".
- **Variation dimensions and history.** Löwy, Righting Software ([review](https://www.infoq.com/articles/book-review-righting-software)): "decompose based on volatility"; functional decomposition "cannot handle change, because by definition the change is not in any one place." Tornhill, [Kill the Clones](https://www.accu.org/journals/overload/24/134/tornhill_2269/) (Overload 134, from *Your Code as a Crime Scene*): "Temporal Coupling isn't measured from code; Temporal Coupling is measured from the evolution of the code"; `variant-history.mjs` applies it to the commits that added a variant.
- **No abstraction ahead of its variants.** The rule of three (Don Roberts, in Fowler's *Refactoring*; [summary](https://en.wikipedia.org/wiki/Rule_of_three_(computer_programming))) and Fowler, [Yagni](https://martinfowler.com/bliki/Yagni.html): no code for "a feature that isn't yet being made available"; "Yagni only applies to capabilities built into the software to support a presumptive feature, it does not apply to effort to make the software easier to modify". Hence ports over variants that exist, or where Martin's dependency rule above asks for one.
- **Tools establish facts, the model judges.** Bellur et al., [Leveraging LLMs, IDEs, and Semantic Embeddings for Automated Move Method Refactoring](https://arxiv.org/abs/2503.20934) (ICSME 2025): "up to 80% of the suggestions are hallucinations"; the authors "automatically filter LLM hallucinations using static analysis from IDEs". Hence the `file:line` under every directory, the evidence rule on `Moves`, and the history read by a script instead of the model's count.
- **A dependency the project lacks is the user's choice, not the model's memory.** Spracklen et al., [We Have a Package for You! A Comprehensive Analysis of Package Hallucinations by Code Generating LLMs](https://arxiv.org/abs/2406.10279) (USENIX Security 2025): "the average percentage of hallucinated packages is at least 5.2% for commercial models and 21.7% for open-source models". Wang et al., [LLMs Meet Library Evolution: Evaluating Deprecated API Usage in LLM-based Code Completion](https://arxiv.org/abs/2406.09834) (ICSE 2025): "LLMs may struggle to use correct and up-to-date Application Programming Interfaces (APIs) due to the rapid and continuous evolution of libraries." Larios Vargas et al., [Selecting third-party libraries: The practitioners' perspective](https://arxiv.org/abs/2005.12574) (ESEC/FSE 2020): "26 technical, human, and economic factors that developers take into consideration when selecting a software library"; "How developers select libraries depends on the type of project".
